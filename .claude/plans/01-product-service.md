## 2. Objective

The Product Service will serve as the central catalog for the e-commerce platform, managing product identity and details while aggregating real-time data (category names and stock status) from the Category and Inventory services to provide a comprehensive view to the client.

## 3. Existing Context

The Product Service is one of the first services in the build order. It relies on the Category Service (Port 8082) and Inventory Service (Port 8083) for data aggregation. It will be exposed via the API Gateway (Port 8080).

## 4. Scope

### In Scope
- Product CRUD operations (Create, Update, Get, List).
- Integration with Category Service via OpenFeign to fetch category names.
- Integration with Inventory Service via OpenFeign to create initial stock and check stock status.
- Implementation of Repository, DTO, and Factory patterns.
- Global exception handling for 404 and 400 errors.
- Unit, Controller, and Integration tests.

### Out of Scope
- Category hierarchy management.
- Stock level management (handled by Inventory Service).
- Pricing logic (handled by Pricing Service).
- JWT validation (handled by API Gateway).

## 5. Architecture

Client
  |
API Gateway
  |
Product Service
  |
+--> Category Service (Synchronous REST)
+--> Inventory Service (Synchronous REST)

Product Service owns the Product entity. It calls Category Service to resolve `categoryId` to `categoryName` and calls Inventory Service to resolve `productId` to `inStock` status.

## 8. API Implementation Plan

### Create Product
- HTTP method: `POST`
- path: `/products`
- request DTO: `ProductRequest` (name, description, price, categoryId)
- validation: `name` (@NotBlank), `price` (@NotNull), `categoryId` (@NotNull)
- response DTO: `ProductResponse`
- status codes: `200 OK`, `400 Bad Request`
- authentication/authorization: ADMIN
- downstream calls: `POST /inventory` (Create initial stock with quantity 0)
- error behavior: Log failure of inventory creation but return product success.

### Get Product
- HTTP method: `GET`
- path: `/products/{id}`
- request DTO: N/A
- validation: UUID format for `{id}`
- response DTO: `ProductResponse` (id, name, description, price, categoryName, inStock)
- status codes: `200 OK`, `404 Not Found`
- authentication/authorization: Public
- downstream calls: `GET /categories/{id}`, `GET /inventory/{productId}`
- error behavior: Fallback to "Unknown Category" and `inStock = false` on downstream failure.

### List Products
- HTTP method: `GET`
- path: `/products`
- request DTO: N/A
- validation: N/A
- response DTO: `List<ProductResponse>`
- status codes: `200 OK`, `500 Internal Server Error`
- authentication/authorization: Public
- downstream calls: Multiple calls to Category and Inventory services for each product in the list.
- error behavior: Individual product aggregation failures should not fail the entire list.

## 9. Service Layer Plan

1. **Create Product**:
    - Validate request.
    - Use `ProductFactory` to create `Product` entity.
    - Save `Product` entity to database.
    - Trigger asynchronous-style synchronous call to Inventory Service to create stock with quantity 0.
2. **Get Product**:
    - Retrieve `Product` from database.
    - Fetch `categoryName` from Category Service via `CategoryClient`.
    - Fetch `quantity` from Inventory Service via `InventoryClient`.
    - Map to `ProductResponse` using `ProductFactory`.
3. **List Products**:
    - Retrieve all `Product` entities.
    - For each product, perform aggregation (Category + Inventory).
    - Return list of `ProductResponse`.

## 10. Design Pattern Implementation Plan

### Repository Pattern
- Where: `ProductRepository`
- Why: Standard JPA abstraction for Product entity.
- Main participants: `ProductRepository` extending `JpaRepository`.

### DTO Pattern
- Where: `ProductRequest`, `ProductResponse`
- Why: Decouples API from database schema and prevents leaking internal `categoryId`.
- Main participants: `ProductRequest`, `ProductResponse`.

### Factory Pattern
- Where: `ProductFactory`
- Why: Centralizes mapping between Entities and DTOs.
- Main participants: `ProductFactory` (mapping methods).

### Facade / Aggregation
- Where: `ProductServiceImpl`
- Why: Aggregates data from Product DB, Category Service, and Inventory Service.
- Main participants: `ProductServiceImpl`, `CategoryClient`, `InventoryClient`.

## 11. Remote Communication Plan

| Caller | Provider | Endpoint | Purpose | Failure Handling |
|--------|----------|----------|---------|------------------|
| Product | Category | `/categories/{id}` | Fetch category name | Fallback to "Unknown Category" |
| Product | Inventory | `/inventory/{productId}` | Check stock status | Fallback to `inStock = false` |
| Product | Inventory | `/inventory` | Create initial stock | Log failure; do not roll back product creation |

- **Timeout**: 2-second read timeout.
- **Retry**: No retries for POST requests.
- **Circuit Breaker**: To be implemented later using Resilience4j.

## 12. Exception Handling Plan

- **ProductNotFoundException**: Thrown when `productId` is not found. Maps to 404 Not Found.
- **MethodArgumentNotValidException**: Thrown by Spring Validation. Maps to 400 Bad Request.
- **Global Exception Handler**: Uses `@RestControllerAdvice` to map these exceptions to a standardized error response shape: `{ "error": "...", "id": "..." }`.

## 13. Security Plan

- **Authentication**: Handled by API Gateway via JWT.
- **Authorization**: `POST /products` requires `ADMIN` role. Public access for `GET` endpoints.
- **Sensitive Data**: No internal IDs or passwords exposed in responses.

## 19. Risks and Failure Scenarios

- **Downstream Service Unavailable**: Category or Inventory services might be down. Handled by fallbacks.
- **Invalid Category ID**: A product might be created with a `categoryId` that doesn't exist. Handled by "Unknown Category" fallback.
- **Remote Call Latency**: Synchronous calls to downstream services can increase response time.
