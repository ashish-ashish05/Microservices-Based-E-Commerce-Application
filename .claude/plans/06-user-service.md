## 2. Objective

The User Service will manage user registration, profiles, and the association between users and their security roles, providing the primary source of truth for user identity data and credential lookup for the Auth Service.

## 3. Existing Context

The User Service depends on the Role Service (Port 8085) to validate roles during registration. It is consumed by the Auth Service (Port 8085 - *Note: Auth and Role services may share ports in some configs, check specification*) for user lookup during login.

## 4. Scope

### In Scope
- User registration (including BCrypt password hashing).
- User profile management (Get, Update).
- Internal user lookup API for the Auth Service.
- Integration with Role Service via OpenFeign to validate roles.
- Implementation of Repository, DTO, and Service Layer patterns.
- Global exception handling for 404, 409, and 403 errors.
- Unit, Controller, and Integration tests.

### Out of Scope
- JWT generation and validation (handled by Auth Service and API Gateway).
- Role metadata management (handled by Role Service).
- Registration confirmation emails (deferred to Notification Service).

## 8. API Implementation Plan

### Register User
- HTTP method: `POST`
- path: `/api/users`
- request DTO: `UserRegistrationRequestDTO` (email, password, fullName, roleId)
- validation: `email` (format), `password` (complexity), `fullName` (NotBlank), `roleId` (NotNull)
- response DTO: `UserResponseDTO`
- status codes: `201 Created`, `400 Bad Request`, `409 Conflict` (email exists), `404 Not Found` (invalid role)
- authentication/authorization: Public
- downstream calls: `GET /api/roles/{roleId}` (Role Service)
- error behavior: Throw `InvalidRoleException` if role does not exist.

### Get User Profile
- HTTP method: `GET`
- path: `/api/users/{userId}`
- request DTO: N/A
- validation: UUID format for `{userId}`
- response DTO: `UserResponseDTO` (id, email, fullName, roleId)
- status codes: `200 OK`, `404 Not Found`, `403 Forbidden`
- authentication/authorization: User (self) or ADMIN
- downstream calls: None
- error behavior: Throw `UserNotFoundException`.

### Update User Profile
- HTTP method: `PUT`
- path: `/api/users/{userId}`
- request DTO: `UserUpdateRequestDTO` (fullName, email)
- validation: `email` (format)
- response DTO: `UserResponseDTO`
- status codes: `200 OK`, `404 Not Found`, `400 Bad Request`
- authentication/authorization: User (self) or ADMIN
- downstream calls: None
- error behavior: Throw `UserNotFoundException`.

### User Lookup (Internal)
- HTTP method: `GET`
- path: `/api/users/lookup`
- request DTO: N/A (query param: `email`)
- validation: `email` (NotNull)
- response DTO: `UserAuthDTO` (id, passwordHash, roleId)
- status codes: `200 OK`, `404 Not Found`
- authentication/authorization: Internal (Auth Service only)
- downstream calls: None
- error behavior: Throw `UserNotFoundException`.

## 9. Service Layer Plan

1. **Register User**:
    - Validate `UserRegistrationRequestDTO`.
    - Call `RoleServiceClient` to verify the `roleId` exists in the Role Service.
    - Hash the password using `BCryptPasswordEncoder`.
    - Save the `User` entity to the database.
2. **Get Profile**:
    - Retrieve `User` by ID.
    - Map to `UserResponseDTO` (ensure `passwordHash` is excluded).
3. **Update Profile**:
    - Retrieve `User` by ID.
    - Update `fullName` and `email`.
    - Save `User` entity.
4. **User Lookup**:
    - Retrieve `User` by email.
    - Map to `UserAuthDTO` (includes `passwordHash` and `roleId`).

## 10. Design Pattern Implementation Plan

### Repository Pattern
- Where: `UserRepository`
- Why: Standard JPA abstraction.
- Main participants: `UserRepository` extending `JpaRepository`.

### DTO Pattern
- Where: `UserRegistrationRequestDTO`, `UserResponseDTO`, `UserAuthDTO`
- Why: Protects internal entity structure and prevents password hash leakage.
- Main participants: `UserRegistrationRequestDTO`, `UserResponseDTO`, `UserAuthDTO`.

### Service Layer Pattern
- Where: `UserService`
- Why: Centralizes business logic (hashing, remote role checks, persistence).
- Main participants: `UserService` interface and `UserServiceImpl`.

## 11. Remote Communication Plan

| Caller | Provider | Endpoint | Purpose | Failure Handling |
|--------|----------|----------|---------|------------------|
| User | Role | `/api/roles/{roleId}` | Validate role exists | Circuit breaker + Fallback to 400 Bad Request |

- **Timeout**: 2-second read timeout.
- **Retry**: No retries for role validation.
- **Circuit Breaker**: To be implemented using Resilience4j.

## 12. Exception Handling Plan

- **UserNotFoundException**: Thrown when `userId` is not found. Maps to 404 Not Found.
- **EmailAlreadyExistsException**: Thrown when registering with an existing email. Maps to 409 Conflict.
- **InvalidRoleException**: Thrown when the provided `roleId` is invalid. Maps to 404 Not Found.
- **AccessDeniedException**: Thrown when a user tries to modify another user's profile. Maps to 403 Forbidden.
- **Global Exception Handler**: Uses `@RestControllerAdvice` to map exceptions to a standardized error response shape.

## 13. Security Plan

- **Authentication**: Profile and Update APIs require a valid JWT.
- **Authorization**: Profile access restricted to the owner or ADMIN.
- **Password Handling**: Use BCrypt. Never log passwords or hashes.
- **Internal APIs**: `/api/users/lookup` restricted to internal traffic.

## 19. Risks and Failure Scenarios

- **Role Service Unavailable**: Registration fails if Role Service is down. Handled by fallback to 400 Bad Request.
- **Duplicate Emails**: Handled by `EmailAlreadyExistsException`.
- **Unauthorized Profile Access**: Handled by `AccessDeniedException`.
