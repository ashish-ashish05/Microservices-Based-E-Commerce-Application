# 08. API Gateway JWT Security Specification

## 1. Document Status

- Service: API Gateway (Security Enhancement)
- Build Order: 08
- Assignment: 2
- Status: Proposed
- Scope: Specification only

## 2. Purpose

The purpose of this specification is to enhance the existing API Gateway (04-api-gateway) with robust JWT (JSON Web Token) validation. The API Gateway will act as the primary security enforcement point, ensuring that only authenticated requests with valid tokens can access protected microservices, while allowing public access to authentication and registration endpoints.

## 3. Responsibilities

- Intercept all incoming requests to protected routes.
- Extract the JWT from the `Authorization` header (Bearer token).
- Validate the JWT signature, expiration, and issuer using a shared secret or public key.
- Extract user identity and roles from the JWT claims.
- Forward the extracted user identity and roles to downstream services via custom HTTP headers.
- Block requests with missing, invalid, or expired tokens with a `401 Unauthorized` response.
- Maintain a list of public routes that bypass JWT validation.

## 4. Non-Responsibilities

- Generating JWT tokens (Responsibility of `Auth Service`).
- Managing user credentials or passwords (Responsibility of `User Service`).
- Managing user roles or permissions persistence (Responsibility of `Role Service`).
- Implementing business logic for the microservices.

## 5. Service Boundary

- **Data Ownership**: Owns no business data. It uses configuration for JWT secrets and public route lists.
- **Domain Ownership**: Owns the "Security Perimeter" and "Token Validation" domain.
- **External Dependencies**: 
    - `Auth Service` (Indirectly: the Gateway validates tokens generated by the Auth Service).
- **Boundary Justification**: Centralizing JWT validation at the Gateway prevents every individual microservice from having to implement security logic, ensuring consistent security policy enforcement across the entire system.

## 6. Architecture

Client
  |
  | (Request + JWT)
  v
API Gateway
  |
  +---> [ JWT Validation Filter ] --- (Invalid Token) ---> 401 Unauthorized
  |           |
  |           +--- (Valid Token) --- [ Header Enrichment ]
  |                                          |
  |                                          v
  +------------------------------------------+
  |
  +---> Product Service (with X-User-Id, X-User-Role headers)
  |
  +---> Category Service
  |
  +---> (Other Protected Services...)

## 7. Service-to-Service Communication

The Gateway does not call other services to validate tokens; it validates them locally using the JWT secret. However, it enriches the request before forwarding.

| Consumer | Provider | Method | Endpoint | Purpose | Failure Consideration |
|----------|----------|--------|----------|---------|-----------------------|
| Gateway  | All Protected Services | ALL | Various | Forward authenticated request | Downstream 5xx handled by Gateway |

**Synchronous Communication Policy**:
- **Timeouts**: Standard Gateway timeouts apply.
- **Header Enrichment**: The Gateway adds `X-User-Id` and `X-User-Role` to the request headers to inform downstream services of the authenticated user's context without them needing to re-parse the JWT.

## 8. API Specification

The Gateway does not expose new business APIs. It modifies the behavior of existing routes.

### Protected Routes
- **Path**: `/products/**`, `/orders/**`, `/cart/**`, etc.
- **Requirement**: Valid JWT in `Authorization: Bearer <token>` header.
- **Success**: Request forwarded to downstream service with identity headers.
- **Error**: `401 Unauthorized` if token is missing or invalid.

### Public Routes
- **Path**: `/auth/**`, `/users/register`
- **Requirement**: None.
- **Success**: Request forwarded directly to downstream service.

## 9. Data Model

The API Gateway remains stateless and does not use a database.

## 10. DTOs

The Gateway does not define business DTOs for this task. It interacts with the JWT claim set.

## 11. Business Rules

- **Token Format**: Must follow the `Bearer <token>` convention.
- **Expiration**: Tokens past their `exp` claim must be rejected.
- **Issuer**: Tokens must be issued by the trusted `Auth Service`.
- **Public Bypass**: Requests to `/auth/**` must never be subjected to JWT validation.
- **Header Sanitization**: The Gateway must strip any incoming `X-User-Id` or `X-User-Role` headers from the client to prevent identity spoofing.

## 12. Design Patterns

### Pattern: Intercepting Filter
- **Where**: Spring Cloud Gateway `GlobalFilter` or `GatewayFilter`.
- **Why**: To implement a cross-cutting security concern (JWT validation) that applies to multiple routes.
- **Problem it solves**: Avoids duplicating security logic across different route definitions.

### Pattern: Adapter (JWT Decoder)
- **Where**: Security Utility class.
- **Why**: To encapsulate the JJWT library logic for parsing and validating tokens.
- **Problem it solves**: Decouples the gateway's filter logic from the specific JWT library implementation.

## 13. Dependencies

### Required
- `spring-boot-starter-security`: Basic security framework.
- `spring-security-oauth2-resource-server`: Provides standard support for JWT-based resource servers.
- `spring-security-oauth2-jose`: JSON Object Signing and Encryption (JOSE) support for JWT decoding.
- `io.jsonwebtoken:jjwt-api`, `jjwt-impl`, `jjwt-jackson`: (Alternatively use Spring Security's native Nimbus-based decoder, but JJWT is specified in `CLAUDE.md` for Auth Service, so consistency is preferred).

### Optional / Later
- `spring-cloud-starter-circuitbreaker-resilience4j`: For handling downstream failures during forwarded requests.

## 14. Configuration

```properties
server.port=8080

# JWT Configuration
jwt.secret=your-very-secure-shared-secret-key-here
jwt.issuer=auth-service

# Public Route Patterns (Comma-separated)
gateway.security.public-routes=/auth/**,/users/register
```

## 15. Security

- **Token Validation**: Signature check using HS256 (Symmetric) or RS256 (Asymmetric) as defined in Auth Service.
- **Identity Propagation**: Use `X-User-Id` and `X-User-Role` headers for downstream services.
- **Secret Management**: The `jwt.secret` must be loaded from an environment variable in production, not hard-coded.
- **Spoofing Prevention**: Ensure internal headers are cleared before enrichment.

## 16. Exception and Error Handling

| Exception | Trigger | HTTP Status | Response Shape | Handling |
|-----------|---------|-------------|----------------|-----------|
| `JwtAuthenticationException` | Invalid signature/expired token | 401 Unauthorized | `{ "error": "Invalid or expired token" }` | Global Gateway Exception Handler |
| `AccessDeniedException` | Valid token but insufficient role | 403 Forbidden | `{ "error": "Insufficient permissions" }` | Global Gateway Exception Handler |

## 17. Transaction Boundaries

Not applicable. The Gateway is stateless.

## 18. Validation

- **Header Presence**: Check for `Authorization` header on protected routes.
- **Prefix Validation**: Ensure the header starts with `Bearer `.
- **Claim Validation**: Ensure `sub` (subject) and `roles` claims are present in the token.

## 19. Testing Strategy

### Unit Tests
- Test the `JwtUtil` class for various token scenarios: valid, expired, wrong signature, missing claims.

### Controller / Integration Tests
- **Public Access**: Verify `/auth/login` returns 200 (or 4xx depending on body) without a token.
- **Protected Access (No Token)**: Verify `/products` returns 401.
- **Protected Access (Invalid Token)**: Verify `/products` returns 401.
- **Protected Access (Valid Token)**: Verify `/products` returns 200 (mocking downstream).
- **Header Enrichment**: Verify that the request sent to the mocked downstream service contains the correct `X-User-Id` and `X-User-Role` headers.

### Failure Tests
- Verify behavior when the JWT secret is incorrectly configured.

## 20. Observability

- **Security Logs**: Log failed authentication attempts (including reason and client IP).
- **Audit**: Log the User ID for every request to protected resources.

## 21. Implementation Sequence

1. Add required security dependencies to `pom.xml`.
2. Create a `JwtUtil` component to handle parsing and validation of JJWT tokens.
3. Implement a `JwtAuthenticationFilter` (extending `AbstractGatewayFilterFactory` or as a `GlobalFilter`).
4. Configure the filter to:
    - Identify public routes.
    - Validate the token for protected routes.
    - Strip existing identity headers.
    - Add enriched identity headers to the request.
5. Integrate the filter into the Gateway routing configuration.
6. Implement a global exception handler to return standardized 401/403 responses.
7. Add configuration properties for the JWT secret and public routes.
8. Write unit tests for `JwtUtil`.
9. Write integration tests using `WebTestClient` to verify the security flow.
10. Run `./mvnw clean test` and verify.

## 22. Acceptance Criteria

- [ ] Requests to `/auth/**` and `/users/register` are allowed without a token.
- [ ] Requests to all other routes without a token result in `401 Unauthorized`.
- [ ] Requests with expired or tampered tokens result in `401 Unauthorized`.
- [ ] Requests with a valid token are forwarded to downstream services.
- [ ] Downstream services receive `X-User-Id` and `X-User-Role` headers.
- [ ] Any client-provided `X-User-Id` headers are removed before forwarding.
- [ ] No business logic is added to the Gateway.
- [ ] `./mvnw clean test` passes.
- [ ] Dependency versions follow `CLAUDE.md`.

## 23. Out of Scope

- Implementing the actual login/registration logic.
- Token revocation/blacklist (e.g., using Redis).
- Complex OAuth2 flow (using simple JWT for learning).

## 24. Decisions and Open Questions

- **Decision**: Use the same symmetric secret for both Auth Service (signing) and Gateway (validation) for initial simplicity.
- **Decision**: Use `X-` headers for identity propagation as they are standard for internal microservice communication.
- **Question**: Should roles be passed as a comma-separated list in `X-User-Role`? (Decision: Yes, comma-separated).
